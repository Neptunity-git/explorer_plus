# 0007: MOD 開発者が喜ぶための設計方針

- 日付: 2026-10-13
- 状態: 採用中

発案者の方針「技術スタックや設計は、MOD 開発者が最大限喜ぶように作る」を、具体的な決まりにしたもの。
ADR 0002（1つのデータ、たくさんのビュー）と ADR 0006（Tauri ＋ TypeScript）を前提にする。

## 判断1: ビューの MOD は「フォルダ1つ＝manifest.json ＋ JavaScript」。ビルドなしで動く

**決めたこと**：ビューの MOD は、次の形のフォルダ1つ。

```
my-view/
  manifest.json   … 名前、使う情報の宣言（ADR 0002 判断4）、対応する API の版
  index.js        … 入口。ふつうの JavaScript（ES モジュール）
  （画像・CSS など、好きなファイル）
```

TypeScript や React を使いたい人は、自分でビルドして index.js を出せばよい。型の定義ファイル（.d.ts）を配るので、
TypeScript なら書きながら補完とエラーチェックが効く。

**検討した選択肢**：

- 案A（採用）：ビルドなしでも動く。使いたい人だけビルドする
- 案B（却下）：決まったビルドの道具（特定のフレームワーク）を必須にする。はじめての人の入口が狭くなる。
  道具の流行りが変わると MOD が古びる

**選んだ理由**：「メモ帳で index.js を書いたら動いた」が一番うれしい入口。上級者の自由も奪わない。

**後で見直す条件**：MOD の数が増えて、配布の形（1ファイルにまとめる、など）を決める必要が出たとき。

## 判断2: MOD は自分専用の iframe の中で動き、好きなライブラリを使える

**決めたこと**：各ビューは、サンドボックス化した iframe の中で動く。ページ（DOM）を丸ごと1つ持てるので、
Three.js・React・PixiJS・素の JavaScript など、好きなライブラリで描ける。本体とのやりとりは、
決まった API（判断3）だけで行う。MOD が止まったり壊れたりしても、本体と他のタブは巻き込まれない。

**検討した選択肢**：

- 案A（採用）：MOD ごとの iframe
- 案B（却下）：本体の画面に直接描かせる（本体と同じ場所で動かす）。速いが、MOD が本体の中身に触れて
  しまい、ADR 0002 判断3（読んで描くだけ）を守れない。1つの MOD の不具合でアプリ全体が止まる
- 案C（却下）：本体が用意した部品（ボタン・リスト・3D の箱など）の組み合わせだけで描かせる。安全だが、
  本体が用意していない見せ方は作れず、MOD の面白さが本体の想像力の範囲に閉じる

**選んだ理由**：安全（閉じ込められる）と自由（何でも描ける）を両立できる。

**後で見直す条件**：iframe を通すやりとりが遅くて、大きなフォルダの表示が重いと分かったとき。

## 判断3: API は小さく、型が付いていて、版（バージョン）を持つ

**決めたこと**：MOD が使う API は、次の3種類に絞る。

- **読む**：manifest で宣言した情報（フォルダの階層、名前・種類・サイズ、リンクなど）を受け取る。
  変化したら知らせを受け取る
- **自分の構造を保存する**：このビュー専用の構造（仮想ディレクトリ、配置など。ADR 0005 判断4）を読み書きする。
  保存の仕方と、名前変更・移動への強さ（ファイルID）は本体が面倒を見る
- **本体に頼む**：「このファイルを開いて」「ごみ箱へ送って」などを頼む。本体が確認し、アニメーションを付けて実行する

API には版を付け、manifest に「どの版向けに作ったか」を書く。本体を更新しても、古い版の MOD が動き続けるようにする。

**検討した選択肢**：

- 案A（採用）：小さく、型付きで、版を持つ
- 案B（却下）：本体の内部をそのまま公開する。最初は何でもできて便利だが、本体を直すたびに MOD が壊れる。
  MOD 作者が一番嫌がること

**選んだ理由**：覚えることが少なく、作った MOD が長く動き続けることが、MOD 作者にとって一番の価値。

**後で見直す条件**：API に足りないものが見つかったとき（版を上げて足す。古い版も動かし続ける）。

## 判断4: 標準のビューも MOD と同じ形で作り、そのまま手本にする

**決めたこと**：Win11 風・樹形図・ボクセルなどの標準ビューも、判断1の形のフォルダとして作る
（ADR 0002 判断2）。MOD 作者は、標準ビューをコピーして書き換えるところから始められる。

**検討した選択肢**：

- 案A（採用）：標準ビューを手本として読める形で置く
- 案B（却下）：標準ビューは本体に埋め込み、手本は別に書く。手本が本物とずれていき、古くなる

**選んだ理由**：動いている本物が、一番正確で、一番古びない説明書になる。

**後で見直す条件**：特になし。

## 判断5: アプリなしでも、ブラウザだけで MOD を作れるようにする

**決めたこと**：本体の代わりに、見本のデータを渡す「練習用の本体」（モック）を用意する。MOD 作者は、
アプリを入れなくても、普通のブラウザで MOD を開いて作れる。アプリの開発モードでは、MOD のファイルを
保存したら、そのビューが自動で読み込み直される（ホットリロード）。

**検討した選択肢**：

- 案A（採用）：モックとホットリロードを用意する
- 案B（却下）：アプリの中でしか試せない。1行直すたびにアプリを再起動することになり、作るのが面倒になる

**選んだ理由**：「直す → すぐ見える」の速さが、作る楽しさを決める。モックは、本体のテスト（Qwen が書く）にも使える。

**後で見直す条件**：特になし。

## 判断6: MOD の閉じ込めは「sandbox」と「CSP」の2重にする

**決めたこと**：MOD の iframe は、`sandbox="allow-scripts"`（`allow-same-origin` を付けない）にしたうえで、
本体が CSP（通信先の制限）を必ず付ける。MOD のデータの保存は localStorage ではなく、本体の API で行う。

**検討した選択肢**：

- 案A（採用）：sandbox と CSP の2重
- 案B（却下）：sandbox だけ。技術の確認（`spikes/platform-check/RESULTS.md`）で、sandbox だけでは MOD が
  インターネットに出られ、Tauri の通信口にも要求が届く（Tauri の送り元の確認で拒否はされる）と分かった。
  守りが Tauri 側の1枚だけになる

**選んだ理由**：MOD が勝手にファイルの情報を外へ送れないことを、2枚の守りで確実にする。sandbox の副作用で
MOD は localStorage を使えないので、保存は本体が面倒を見る（判断3の「自分の構造を保存する」と一致）。

**後で見直す条件**：「ネットから情報を取ってくる MOD」（天気を表示する、など）の要望が出たとき（ユーザーが許可した
通信先だけ開ける）。

## 用語メモ

- CSP（Content Security Policy）：Webページに「どこと通信してよいか、どのスクリプトを動かしてよいか」を指示するルール
- オリジン：Webページの「出どころ」（`https://example.com` など）。sandbox の iframe は出どころなし（`null`）扱いになる

- manifest.json：MOD の名前や設定を書く、MOD の名刺のようなファイル
- ES モジュール：今の JavaScript の標準的なファイルの分け方（import / export を使う）
- DOM：Webページの中身（見出し、ボタン、画像など）を、プログラムから触れる形にしたもの
- 型の定義ファイル（.d.ts）：「この関数は何を受け取り、何を返すか」を書いたファイル。エディタの補完が効く
- モック：本物の代わりに、決まった見本の動きをする偽物
- ホットリロード：ファイルを保存した瞬間に、画面が自動で更新される仕組み
