# 0040: 共有フォルダに、PC ごとの「追記だけの記録」を書く／MOD ごとの匿名の ID と表示名

- 日付: 2026-10-27
- 状態: 採用中（ADR 0022 判断1 の folderData に並ぶもの。ADR 0001 判断3 の範囲の中）

**きっかけ**：付箋ボード MOD の作者からのお願い（優先度：高の3つ）。OneDrive や NAS の共有フォルダを一つの「ワールド」にして、
最大50人ほどで付箋を貼り合う MOD を、サーバーなしで作りたい。今の API では次のことができない。

- 書けるのは `files.create`（新規作成だけ）なので、投稿のたびにファイルが1つ増える（50人で1年使うと数万ファイル）
- `onChanges` は開いているフォルダの直下しか知らせないので、隠しフォルダの奥に同期で届いた投稿に気づけない
- 誰が書いたかを知る方法がなく、表示名を自己申告するしかない。他人の付箋に「消した印」を付けるなりすましも防げない

ADR 0001 判断3「自前の共有・同期の仕組みは作らない」とはぶつからない。共有と同期は OneDrive などに任せたまま、
本体は「同期でぶつからない書き方」と「誰が書いたかの確かめ」という部品を出すだけ。付箋ボードそのものは MOD が作る（ADR 0023 の方針）。

## 判断1: `folderLog`：フォルダの中に、PC ごと・月ごとの追記だけのファイルを本体が書く

**決めたこと**：

- `ep.folderLog.append(folder, data)`：本体が `<フォルダ>/.explorer_plus/log.<MOD の id>/<書いた人の ID>/<年-月>.jsonl` の末尾に1行足す
  （jsonl：1行に1件の JSON を書く形式）。`.explorer_plus` は ADR 0022 と同じ隠しフォルダ
- 1件ごとに、本体が `id`（ランダムな 32 文字）・`t`（本体の時計の時刻）・署名を付ける。`data` は MOD が決める JSON（64KB まで）
- `ep.folderLog.read(folder, { since })`：全員のファイルを読み、署名を確かめた記録だけを返す。`cursor` を次の `since` に渡すと、続きから読める。
  1回で読むのは 2MB まで（残りがあれば `more: true`）
- 書けるのは自分のファイルだけ（本体が自分の ID の場所にしか書かない）。上書き・削除の API は作らない。「消した」は MOD が記録として足す
- 開いているフォルダの記録が増えたら `ep.onFolderLog(cb)` で知らせる（ほかの PC から同期で届いたときも、この PC のほかのタブが足したときも）

**「人ごと」ではなく「PC ごと」にした理由**：同期でぶつかるのは、同じファイルを2台の PC が同時に書いたとき。
同じ人が大学の PC と家の PC から書けば、「1人1ファイル」でもぶつかる。PC ごとなら、1つのファイルを書くのはいつも1台だけになる。

**月ごとに分けた理由**：OneDrive は、書き足すたびにファイル全体を送り直す。1年分を1つのファイルにすると、1回の投稿で数 MB を送ることになる。

**書き方の細かいこと**：

- 書き込みの途中で止まって半端な行が残っても、読むときは改行で終わっていない最後の行を読まない（`cursor` も進めない）。
  次に書くときは、先に改行を足してから書く
- 同期の道具がファイルを握っていて書けないときは、少し待って数回やり直す
- 同じ行が2回入っても（同期の道具のやり直しなど）、1回の `read` の中では `id` で1つにする

**知らせの作り方（ADR 0018 の見張りは使わない）**：最初に考えた案は、記録のフォルダを下の階層まで見張ることだった。しかし、

- 記録のフォルダは、誰かが最初に書くまで無い（無いフォルダは見張れない）
- NAS では、変更の知らせが来ないことがある
- 同期の遅れはもともと数秒〜数分あるので、数秒おきに確かめれば遅さは目立たない

ので、開いているフォルダの記録のファイルの大きさと更新時刻を、表示中のタブは 5 秒おき、裏のタブは 20 秒おきに確かめる（ファイルの中身は読まない）。
アプリの窓に戻ってきたときにも確かめる。

**検討した選択肢**：

- 案A（採用）：本体が PC ごとのファイルに追記する
- 案B（却下）：`files.create` のまま、MOD が1件1ファイルで作る。数万ファイルになり、同期も一覧も遅くなる
- 案C（却下）：1つのファイルを全員で書き換える（folderData と同じ）。同時に書くと、どちらかが消える（ADR 0022 の「後で見直す条件」そのもの）
- 案D（却下）：ファイル ID なしで、MOD が `.explorer_plus` の中を自由に読み書きする（お願いの4）。追記だけ・自分の分だけ、という約束を本体が守れない

## 判断2: `identity`：MOD ごとの匿名の ID と、本体で決めた表示名・アイコン

**決めたこと**：

- PC ごとに、本体が秘密の値（ランダムな 32 バイト）を1つ作り、Windows の資格情報マネージャーに預ける（ADR 0027 の秘密の設定と同じ置き場所。名前は MOD の id と重ならない形）
- MOD ごとの署名の鍵を、その秘密の値と MOD の id から作る（Ed25519 という署名の方式）。**MOD の ID は、その鍵の公開鍵**（64 文字の16進数）。
  記録のファイルの置き場所の名前にもなり、読む人はそれで署名を確かめる
- `ep.identity.get()`：`{ id, name, icon }` を返す。名前とアイコンは、本体の「自分の表示名とアイコン」（コマンドの一覧）で決める。
  MOD ごとに、最初に使うとき許可を聞く（表示名は個人の情報で、共有フォルダに書く MOD なら、フォルダを共有している人にも見えるため）。
  まだ表示名が無ければ、許可のあとに決める画面を出す。表示名が変わったら `ep.onIdentity(cb)` で知らせる
- 表示名は記録に自動では入れない。ほかの人に見せたい MOD は、`identity.get()` で得た名前を `data` に入れる（署名されるので、ほかの人が書き換えられない）

**MOD ごとに別の ID にした理由**：同じ ID をどの MOD にも渡すと、別々の MOD が「同じ人だ」と突き合わせられる（通信できる MOD なら外へも送れる）。
付箋ボードに要るのは「このボードの中で同じ人か」だけ。

**署名を本体が自動で付けることにした理由**（お願いでは `ep.identity.sign(data)`）：MOD に署名させると、確かめるのも MOD の仕事になり、
書き忘れ・確かめ忘れが起きる。`folderLog` に組み込めば、`read` が返すのは確かめ済みの記録だけになり、MOD は気にしなくてよい。
`identity.sign` は、記録の外で署名が要る MOD が出てきたら考える。

**分かっていること（限界）**：

- 署名で分かるのは「前の記録と同じ PC（の同じ MOD）が書いた」ことだけ。その人が誰かまでは分からない（表示名は自己申告のまま）
- 同じ人でも、PC が違えば別の ID になる（別の人に見える）
- フォルダに書き込める人は、他人の記録のファイルを丸ごと消せる。偽物は作れない（署名が合わず、`read` に出ない）が、消すのは防げない
- Windows を入れ直す・資格情報が消えると、新しい ID になる

**検討した選択肢**：

- 案A（採用）：PC ごとの秘密から、MOD ごとの鍵を作る
- 案B（却下）：アプリ全体で1つの ID。MOD どうしで突き合わせられる
- 案C（却下）：ログイン（Microsoft アカウントなど）で本人を確かめる。ADR 0001 判断5 と同じく、相手の確認の仕組みを作ることになり、大きすぎる

## 後回しにしたもの（お願いの5〜7）

- 同期の状態（同期済み・送信待ち・共有されているか）：まず `files.properties` で Windows のプロパティ（OneDrive の状態など）が取れるかを MOD 側で試す。NAS には、この情報がない
- 画像を貼る：Windows からビューへのドロップは、今でも「落とせる場所」としてフォルダを出せば、本体がコピーする。クリップボードの画像（ファイルではない絵）と、
  画像の置き場所は、`folderLog` が使われてから考える
- 見ていないときの新着の知らせ：タブを開いていれば、裏にあっても `ui.tab({ badge })` が使える。ビューを開いていないときは、MOD を画面なしで動かし続ける仕組みが要る

**後で見直す条件**：数秒おきの確かめが、NAS や大きなワールドで重いと分かったとき（見張りに切り替える・間隔を延ばす）。
1か月のファイルが大きくなりすぎて困ったとき（週ごとに分ける）。同じ人の PC を「同じ人」と結び付けたい、と言われたとき。
`read` が全員分を最初から読むのが遅いと分かったとき（MOD が `cursor` を `storage` に覚えるよう、ガイドで勧めてある）。
