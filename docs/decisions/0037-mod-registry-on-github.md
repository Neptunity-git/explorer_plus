# 0037: MOD の一覧は、GitHub のリポジトリに置く（自分でサービスを作らない）

- 日付: 2026-10-22
- 状態: 採用中（段階1・2を実施。段階3は未着手）

**困りごと**：いろいろな人が作った MOD を、まとめて探せる場所が無い。ただし、Web サービス（サーバー、ログイン、投稿の確認）を、1人で作って運用するのは重い。
また、教育の場（IDE を初めて使う人向けのイベント）で、「作ったものを人に使ってもらう」「git の運用に触れる」ところまでつなげたい。

## 判断1: 一覧は、GitHub の公開リポジトリ `Neptunity-git/explorer_plus-mods` に置く

**決めたこと**：

- 一覧は `mods.json` 1つ。1件につき `id`・`name`・`description`・`author`・`repo`（`ユーザー名/リポジトリ名`）・省略可の `path`・`network` を書く
- MOD の本体は、作者の GitHub リポジトリの **Releases に付けた zip** で配る。一覧には「どこにあるか」だけを書く（版が上がっても、一覧の書き直しは要らない）
- 載せるのは、**プルリクエスト**（変更の提案）で。メンテナー（今は発案者）が、`manifest.json` と `index.js` を読んで確かめてから取り込む。載せる条件は、そのリポジトリの README に書いた
- `mods.json` の形は、`scripts/check.mjs` を GitHub Actions で自動で確かめる（形の誤りだけ。安全の確認は人が行う）
- 一覧は、本体のリポジトリとは別にする

**検討した選択肢**（却下した案は、却下した理由を必ず書く）：

- 案A（採用）：GitHub のリポジトリを一覧にする。サーバー代・運用が要らず、検索・履歴・通知・プルリクエストによる確認が、そのまま使える
- 案B（却下）：自分で Web サービスを作る。検索や評価はできるが、サーバーの運用、ログイン、不正な投稿への対応が、1人には重すぎる
- 案C（却下）：GitHub の Topics（`explorer-plus-mod` のタグ）だけで探す。登録の手間はゼロだが、確認なしで誰でも載るため、安全面が心配。将来、公式の一覧との併用はありうる
- 案D（却下）：一覧を本体のリポジトリの中に置く。MOD の追加のたびに本体の履歴が増え、権限も分けにくい

**選んだ理由**：サーバーを持たずに済み、確認（プルリクエスト）の体制が、そのまま安全の入口になる。今の入れる仕組み（確認の画面・「通信あり」の表示・同じ id なら更新）をそのまま使える。ADR 0007「MOD 開発者が喜ぶ」にも合う。

**後で見直す条件**：載る MOD が増えて、メンテナー1人では確認が追いつかなくなったとき。悪意のある MOD が載りかけたとき。

## 判断2: アプリの中から探して入れる機能（段階3）は、MOD が10件ほど載ってから作る

**決めたこと**：ホームの MOD の欄に「MOD を探す」を足し、一覧を読んで、Releases の zip を取ってきて、**今の確認画面**に渡す機能は、まだ作らない。
それまでは、一覧のリポジトリを見て、zip を落として入れる。

**検討した選択肢**：

- 案A（採用）：数が増えてから作る。数が少ないうちは、一覧を見るだけで足りる
- 案B（却下）：先に作る。使う人がいないうちに、通信（本体が GitHub に接続する）と更新の確認まで作ると、守る範囲が広がる

**選んだ理由**：先に、運用（確認の仕方）が回るかを、小さく試したい。アプリ側の変更は、そのあとでよい。

**後で見直す条件**：載る MOD が10件ほどになったとき、またはイベントで「アプリの中から入れたい」という声が多く出たとき。
作るときは、通信の許可（ADR 0026・0027）、取ってくる zip の確認（今の入れる処理と同じ検査）、更新の通知のみ（自動更新はしない）を決める。

## 判断3: 初めての人向けの手引きは、git のインストールを前提にしない

**決めたこと**：手引き `work/app/mod-docs/share.md` は、**ブラウザだけ**で、リポジトリの作成・ファイルの置き方・Releases への zip の付け方・プルリクエストまでを説明する。
git や GitHub Desktop は、「次の段階」として後ろに置く。

**検討した選択肢**：

- 案A（採用）：ブラウザだけの手順から始める。ブラウザで「リポジトリ」「公開」「版（タグ）」「プルリクエスト」の考え方に触れられ、コマンドや設定でつまずかない
- 案B（却下）：最初から git のインストールとコマンドを教える。名前とメールの設定、認証、用語の多さで、MOD を作る楽しさが薄れる

**選んだ理由**：イベントの目的は「開発の雰囲気を知り、次のステップへ踏み出す」こと。最初の公開の成功を優先する。

**後で見直す条件**：イベントで、ブラウザの手順で止まる人が多いと分かったとき。

## 判断4: 公開前の安全の確認を、手引きの最初に置く

**決めたこと**：公開すると誰でも見られるので、`share.md` の最初に「公開前に確かめること」（秘密の情報・個人情報・他人の作品・ユーザー名とメールの公開）を置く。
GitHub のアカウントを作ったら、メールアドレスを隠す設定をするよう案内する。年齢の決まり（13歳以上）も書く。

**選んだ理由**：初学者が AI のコードをそのまま公開するときに、API キーや個人の写真を含めてしまう事故が、いちばん起きやすく、取り消しにくいため。

## 用語メモ

- リポジトリ：ファイルと、その変更の履歴を置く箱。GitHub 上のものは、URL で場所が決まる
- プルリクエスト：「ここをこう変えたので取り込んでください」という変更の提案。確認と議論の場にもなる
- Releases：リポジトリに、完成した版（zip など）を付けて配る場所
- GitHub Actions：GitHub 上で、決めた確認や処理を自動で動かす仕組み
- フォーク：他の人のリポジトリを、自分のところにコピーすること
