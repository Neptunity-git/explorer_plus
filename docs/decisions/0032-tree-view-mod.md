# 0032: 樹形図ビューを「ふつうの MOD」として作る。getTree に from を足す

- 日付: 2026-10-15
- 状態: 採用中

土台が安定したので、MOD 作りを始める。最初は樹形図ビュー（企画書の第2段階）。

## 判断1: 樹形図ビューは、標準のビューではなく、ふつうの MOD として作る

**決めたこと**：`work/mods/neo.tree/`（id `neo.tree`）に置き、ホームの「開発中の MOD を追加」で読み込む。zip にして配れる形にする。
本体に同梱するかは、できあがってから決める。

**検討した選択肢**：

- 案A（採用）：ふつうの MOD。MOD 作者と同じ道具（ひな形・ホットリロード・zip）だけで作る
- 案B（却下）：標準のビュー（`views/builtin.tree`）。中身は同じ API で作れるが、MOD 作者の体験を自分で試す機会を逃す

**選んだ理由**：発案者の判断。作りながら、足りない API や MOD 作りの不便に気づける（ADR 0007「MOD 開発者が喜ぶ」）。

**後で見直す条件**：同梱したくなったとき（id を `builtin.tree` にして views へ移す）。

## 判断2: 見た目は「図として描く樹形図」。TUI 風の一覧にはしない

**決めたこと**：今のフォルダを根にして、左から右へ枝分かれする図（箱と曲線）を描く。ドラッグで動かし、ホイールで拡大・縮小する。
色と文字は `tui.css` の色を使って、ほかのビューとなじませる。既定ではフォルダだけを出し、切り替えでファイルも出す
（ファイルを隠しているときは、フォルダの箱に「ファイル n」と数を出す）。

**検討した選択肢**：

- 案A（採用）：図として描く
- 案B（却下）：`tree` コマンドのような字下げの一覧（TUI 風）。軽いが、Win11 風ビューの左の欄（フォルダの木）と見た目の役割が重なる
- 案C（却下）：両方を切り替え。手間が一番大きい

**選んだ理由**：発案者の判断。ADR 0011（Win11 風以外の標準ビューは TUI 風）は標準のビューの決まりで、ふつうの MOD は自由。

**後で見直す条件**：枝が多いフォルダで重い・見づらいとき。

## 判断3: 深い階層は、開いた枝だけを読む。そのため getTree に from を足す

**決めたこと**：最初は今のフォルダから決まった深さ（設定、既定 2）まで読み、枝の ▸ を押したときに、その下を1段読む。
今の `getTree` は今のフォルダからしか読めないので、省略可能な `from`（`{ id, path }`）を足す。`from` のフォルダから下を返す。
`from` の ID が今のものと完全に合わなければ `not-found`（空の ID で確かめを飛ばさない。ほかの API の確かめと同じ。2026-10-15 の見直しで直した）。ほかの決まり（深さ 1〜5、1回にフォルダ 500 個まで）は同じ。

**検討した選択肢**：

- 案A（採用）：クリックで開いた枝だけ読む（`from` を足す）
- 案B（却下）：決まった深さまで一度に読み、その先はダブルクリックでそのフォルダへ移る。API は今のままでよいが、深いところを見渡せない

**選んだ理由**：発案者の判断。`navigate` でどのフォルダへも移れて中身が見えるので、`from` で任意のフォルダを読めても、
MOD が読める範囲は増えない（`tree` の宣言は今までどおり要る）。ただし `navigate` と違い利用者に見えないので、ID の一致は必ず確かめる。足すだけで、古い MOD は壊れない（mod-api-v1「版の決まり」）。

**後で見直す条件**：特になし。

- 枝・節（ノード）：樹形図の1つ1つの箱。フォルダやファイル
