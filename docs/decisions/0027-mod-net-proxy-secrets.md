# 0027: MOD の API を広げる（5）本体が代わりに通信する・API キーを本体が預かる

- 日付: 2026-10-15
- 状態: 採用中（ADR 0026 の「後で見直す条件」に当たったので、本体が代わりに通信する口を足す）

## 背景

ADR 0026 で、MOD は manifest の network に書いた先とブラウザの fetch・img で通信できるようになった。
しかし、試してみると次のサービスが使えなかった：

- 「どこのページからか（Referer）」や、まともな送り元の名前（User-Agent）を求めるもの（OpenStreetMap の公式のタイルは 403）
- ブラウザからの読み込みを許していない（CORS の無い）API
- API キーが要るもの（MOD に書き込むと、zip を開けば誰でも読める）

発案者に「外部のサービスと連携するビューは作りづらいのか」と聞かれ、上の3つの解決を提案し、採用された（OAuth のログインは後で）。

## 判断1: 本体（Rust）が MOD の代わりに通信する口（net.fetch・net.url）を足す

- 宛先は、ADR 0026 と同じく manifest の network に書いた先だけ。転送（リダイレクト）の先も1回ずつ確かめる
- 「explorer_plus の、この MOD から」と名乗る（User-Agent）。クッキーは送らず受け取らない。Cookie・Referer・Origin などは MOD が付けられない
- 名前が PC の中・家の中の住所（127.0.0.1・192.168.x.x など）を指していたら通信しない。
  ブラウザの決まり（CORS）を受けない口なので、悪い MOD がルーターの管理画面などを触るのを防ぐ
- `<img>` などに使えるように、本体が代わりに取ってくる URL（`http://epnet.localhost/<印>`）も出す。スクリプトとしては読み込ませない

**検討した選択肢**：
- 本体が代わりに通信する（採用）
- ブラウザの通信に Referer を付ける工夫（却下：CORS の無い API は解決しない）
- 使えないままにする（却下：地図・天気などのビューが作りにくい）

## 判断2: API キーは、設定の type "secret" にし、本体が資格情報マネージャーに預ける

- 利用者が設定の画面で入れる。値は Windows の資格情報マネージャーに保存し、settings.json には書かない
- MOD には値を見せない（「預けてあるか」だけ）。本体が通信するときに付ける
- 付けてよい宛先（send.origin）と付け方（ヘッダか ?query=）を manifest に書かせ、その宛先への通信のときだけ付ける。
  通信先の別の宛先（MOD 作者のサーバーなど）へキーを送らせないため
- 入れるときの確かめの画面に「本体が預かり、○○だけに送る」と出す。MOD を外すとキーも消す

**検討した選択肢**：
- 資格情報マネージャー（採用：Windows が暗号化して守る。ほかのアプリと同じ仕組み）
- アプリのデータのファイルに保存（却下：平文で残る）
- MOD に値を渡す（却下：MOD が好きな先へ送れてしまう）

**分かっていること**：キーを付けた通信の返事にキーが書かれていれば（入力をそのまま返す試験用のサービスなど）、MOD はそれを読める。サービス側の作りの問題なので、本体では防がない。

**後で見直す条件**：OAuth のログイン（Google カレンダーなど）を使いたい MOD が出てきたとき。
